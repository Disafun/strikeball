# Страйкбол-клуб (Flask + Supabase)

Игроки и администратор работают с одними и теми же данными: профили, мероприятия, записи,
альбомы и фото лежат в облаке Supabase (PostgreSQL + Storage). На устройстве остаётся только
cookie с сессией входа. Требуется **Python 3.11+**.

## Архитектура

```
Браузер (телефон/ПК)  ──►  Flask-приложение  ──►  Supabase
                                                    ├─ Auth      (почта + пароль)
                                                    ├─ Postgres  (таблицы + RLS + триггер вместимости)
                                                    └─ Storage   (bucket "photos")
```
* Flask ходит в Supabase **с токеном самого пользователя и публичным ключом**, поэтому правила
  RLS действуют на каждый запрос. `service_role`-ключа в приложении нет.
* Роль `admin` хранится в таблице `profiles` и выдаётся только вручную через SQL Editor.
  Игрок не может поменять её ни через интерфейс, ни прямым запросом (нет права на колонку и нет RLS-политики).
* Вместимость мероприятия, закрытая/прошедшая игра и дубли записей проверяются **в базе** (триггер с
  блокировкой строки мероприятия + `UNIQUE (event_id, user_id)`), а не только в интерфейсе.
* Телефон и почта игроков видит только администратор (и сам игрок). Остальным доступно имя, возраст, фото
  (представление `public_profiles`).
* Обновление данных: страницы «Мероприятия» и «Статус команды» сами перезагружаются раз в 20 секунд.
  Supabase Realtime не подключён намеренно: для набора команды это избыточно, а лишние постоянные
  соединения расходуют лимиты бесплатного тарифа.

## Первая настройка Supabase (от нуля)

1. Зарегистрируйтесь на https://supabase.com и создайте проект (**New project**, план Free). Запомните пароль БД
   (в приложении он не нужен).
2. **Project Settings → API**: скопируйте *Project URL* и публичный ключ (`anon` или `publishable`).
   Ключ `service_role` в приложение вставлять нельзя.
3. **SQL Editor → New query**: вставьте всё из `supabase/migrations/001_init.sql` и нажмите **Run**.
4. **Authentication → Users → Add user → Create new user**: создайте служебную учётную запись админа
   (почта + длинный пароль, галочка *Auto Confirm User*). Затем в SQL Editor выполните
   `supabase/seed_admin.sql`, заменив в нём `admin@example.com` на эту почту.
5. **Authentication → Sign In / Providers → Email**: для простого старта выключите *Confirm email*
   (иначе новым игрокам придётся подтверждать почту; встроенная отправка писем Supabase сильно ограничена).
   Приложение работает в обоих режимах.
6. Скопируйте `.env.example` → `.env` и заполните: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SECRET_KEY`,
   `ADMIN_PASSWORD`, `ADMIN_ACCOUNT_EMAIL`, `ADMIN_ACCOUNT_PASSWORD`.

## Запуск

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python app.py                      # http://127.0.0.1:5000
```
С телефона в той же Wi-Fi: `http://IP_компьютера:5000`. Если `.env` не заполнен, приложение покажет
страницу «Приложение не настроено».

Вход игрока: почта + пароль (новым — «Создать профиль»). Вход администратора: пароль из `ADMIN_PASSWORD`
(сервер сам входит в служебный админ-аккаунт Supabase).

## Перенос старых данных (если вы уже пользовались локальной версией)

1. Скопируйте старые `strikeball.db` и папку `static/uploads` рядом с этим проектом
   (`strikeball.db` и `old_data/uploads`).
2. Проверка без отправки: `python migrate_from_sqlite.py --dry-run`
3. Перенос (service_role-ключ — только в окружении терминала, не в файлах):
   ```bash
   MIGRATION_SERVICE_ROLE_KEY=... python migrate_from_sqlite.py       # Windows PS: $env:MIGRATION_SERVICE_ROLE_KEY="..."
   ```
   Скрипт создаст аккаунты игроков с **временными паролями** (файл `migrated_users_temp_passwords.csv`):
   раздайте их игрокам, затем удалите файл. Игроки меняют пароль в «Профиль → Сменить пароль».
   Повторный запуск безопасен (прогресс в `migration_state.json`).
4. Проверьте: число игроков в Authentication → Users, строки в Table Editor (`profiles`, `events`,
   `registrations`, `albums`, `photos`), открытие фото в приложении. Старые файлы не удаляются.

## Бесплатный хостинг (по желанию)

Подойдёт любой хостинг Python-приложений (например, Render, Free web service): команда сборки
`pip install -r requirements.txt`, команда запуска `gunicorn app:app` (есть `Procfile`). Задайте те же
переменные, что в `.env`, плюс `SESSION_COOKIE_SECURE=1` и `TRUST_PROXY=1`. Бесплатные веб-сервисы
обычно «засыпают» без трафика, первый заход после паузы медленный.

## Тесты

```bash
python -m unittest discover -s tests -v
```
Тесты используют **эмулятор Supabase** (`tests/fake_supabase.py`), а не настоящее облако: они проверяют
код приложения (потоки входа, ошибки сети, права, галерею). SQL и RLS-политики они не исполняют.

## Ограничения бесплатного тарифа Supabase

Актуальные цифры смотрите на https://supabase.com/pricing. На момент подготовки: 2 бесплатных проекта,
база до 500 МБ, файловое хранилище порядка 0,5–1 ГБ (источники расходятся), трафик 5 ГБ/мес,
50 000 активных пользователей в месяц. **Проект приостанавливается после недели без активности**
(данные сохраняются, но нужно нажать *Restore* в панели). Резервные копии на Free не гарантируются —
периодически выгружайте данные.

## Известные ограничения

* Вход админа по короткому паролю (`5376`) подбирается за считанные минуты; в приложении есть лимит
  5 попыток / 10 минут на IP (в памяти процесса). Для публичного хостинга задайте длинный `ADMIN_PASSWORD`.
* Фото лежат в публичном bucket: открываются по прямой ссылке (имена — случайные), в листинг не попадают.
* Списки читаются до 1000 строк за запрос (лимит PostgREST) — для клуба достаточно.
* Роли только `player` и `admin`; статусы заявок нет (запись есть / нет), как и в прежней версии.
